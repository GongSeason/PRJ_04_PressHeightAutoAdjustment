## 1. 结论摘要

**事实：** 本项目读取相机软件保存到本地/配置目录的 CSV，并独立与 PLC 通信；代码中没有发现与相机软件进程直接通信的实现。自动刷新不是单纯读取 CSV：它依次执行文件定位与尾部读取、数据分析、按需 PLC 通信、图表数据计算和 UI 更新；真实 PLC 模式下还会发生 PLC 读写。

**事实：** CSV 读取已经采用缓存文件句柄，并以共享读/写/删除方式打开文件；常规刷新不会对同一文件每次重新 `CreateFile`，而是重新定位文件、查询文件元数据并从缓存句柄读取尾部。读取字节数受 `WindowSize` 限制，当前工作树配置默认窗口为 200 条，按代码缓冲估算最多读取约 `(200+16)*200 = 43,200` 字节（实际以文件尾长和行长为准）。

**推测：** 现有信息不足以把约 200ms 的 PLC 信号延迟和画面冻结归因于单一代码点。较值得验证的路径是：刷新时对共享存储/文件系统的元数据枚举与读取、长驻 CSV 句柄对相机写入/轮转行为的条件性影响、当前应用与相机应用争用本机资源，以及本应用同时访问同一 PLC 对 PLC 通信/扫描时序造成的影响。代码没有直接控制相机或其画面，以上影响都需现场测量确认。

**推测：** 单纯读取约几十 KB 的尾部数据通常不像是能独自解释稳定 200ms 延迟的充分证据；但每次刷新还会枚举目录、排序 CSV、更新图表、写本地日志，并可能进行多次 PLC 事务，实际存储位置、文件量、控制器配置和系统负载均未知。

本分析不提出最终修复方案，也不建议在缺少生产验证时改变 PLC、握手或控制行为。

## 4. 现有数据流

### 4.1 自动刷新入口

1. **事实：** `MainViewModel.SetupTimer` 设置 `DispatcherTimer`，周期取 `max(1, Settings.RefreshIntervalSeconds)` 秒，构造时不自动启动。
2. **事实：** 用户通过 `ToggleRun` 启动后，定时器开始运行，并立即调用一次 `RefreshDataAsync`。手动重置刷新也会调用该方法。`RefreshDataAsync` 以 `IsLoading` 等条件避免设置面板打开、已有刷新运行或数据源为空时继续执行。
3. **事实：** 刷新开始时设置 `IsLoading`，并暂停心跳定时器以避免心跳与 PLC 调整写入竞争；结束时（包含异常/无数据路径）在 `finally` 中尝试恢复心跳。配方轮询定时器并未在此处一并暂停。

### 4.2 CSV 读取

1. **事实：** `RefreshDataAsync` 调用 `CsvDataProvider.GetLatestDataAsync(WindowSize)`。此方法通过 `Task.Run` 把文件定位、读取与解析放到线程池执行；读取结果随后回到调用方继续处理。
2. **事实：** `GetLatestCsvFile` 每次调用都会检查目录、枚举候选日期目录并从最新日期目录枚举 `*.csv`，按文件名日期、修改时间及名称排序选出一个文件。它不是只靠缓存路径直接读取。
3. **事实：** 文件打开句柄缓存于 `_cachedHandle`。路径不变且句柄有效时复用；首次读取、路径改变、句柄失效时才打开新句柄。打开参数为 `GENERIC_READ`，共享标志包含 `FILE_SHARE_READ | FILE_SHARE_WRITE | FILE_SHARE_DELETE`。
4. **事实：** 每次刷新会通过路径调用 `GetRealFileSize`（实现使用 `GetFileAttributesEx`）取大小，再用 `RandomAccess.Read` 从尾部读最多 `(count+16)*200` 字节，之后以内存方式抽取行并解析。它不读取整个 CSV。
5. **事实：** `CsvDataProvider` 记录“定位/打开/读取/解析”耗时、总耗时和字节数，并可显示超过阈值的调度延迟；这些诊断目前通过性能文本呈现在本应用界面。
6. **事实：** 文件缓存失效或路径切换时，旧句柄会安排后台关闭；待关闭任务最多限制为 5 个，超过时退回同步关闭。常规同一路径读取不触发句柄切换关闭路径。

### 4.3 分析、PLC 与 UI

1. **事实：** CSV 返回后，刷新流程进行重置时间戳过滤、有效值筛选、逐压头新样本计数以及决策仲裁。
2. **事实：** 分析后调用 `SendPlcCommandsAsync`。若决策/模式不要求下发，则不会发生本轮调整写入；否则可使用单头或批量路径。
3. **事实：** 真实 `KeyencePlcAdapter` 的单头调整可能包括：检查 PLC 状态寄存器、写调整寄存器、回读校验、写完成状态标志。批量路径包含批量握手读取、写入、回读和状态标志写入。`SemaphoreSlim` 将 adapter 上的通信串行化。PLC 失败还可能触发连接状态变化及重连调度。
4. **事实：** 配方轮询通过 `ReadInt16Async` 读取程序号，心跳通过 `WriteInt16Async` 写入地址；这些均是本应用与 PLC 的独立通信。是否启用及地址/周期均取决于现场配置。
5. **事实：** `RefreshDataAsync` 完成 PLC 阶段后调用 `PrepareChartData(_currentData)`；虽然该方法注释说后台预计算，但当前调用处没有 `Task.Run` 或其他显式线程切换，所以在异步方法恢复的 UI 上下文中同步执行。随后通过 Dispatcher 更新图表与界面属性。
6. **事实：** PLC adapter 的日志事件处理器调用 `WriteLogToFile`；该方法使用锁保护的同步 `File.AppendAllText`，并可能同步创建日志目录。它没有写相机 CSV，但会增加本机文件系统操作。

## 5. 根因候选（均未确认）

### 候选 A：CSV 同目录/同存储上的文件系统争用

- **事实：** 每次刷新都重新枚举目录和 CSV，并读取文件元数据；对最新目录下 CSV 的排序会需要候选文件的日期/修改时间信息。读取数据本身为尾部小块。
- **推测：** 如果 CSV 位于慢速磁盘、映射盘/网络共享、同步目录，或最新日期目录有大量 CSV，反复枚举/元数据查询可能与相机写入及图像落盘争用设备、网络或杀毒扫描资源；这可能对应画面停顿或相机写 CSV 延迟，但当前没有 I/O 跟踪证据。
- **判断：** 在“刷新与卡顿稳定同步”且数据目录与相机图像/CSV 共用存储的条件下值得优先核实；若是本地 SSD、候选文件很少，可能性会降低。

### 候选 B：持久读句柄对相机写文件/轮转策略的条件性影响

- **事实：** 本项目对正在读取的 CSV 保持读句柄，并允许其他读、写和删除共享；项目注释明确将长驻句柄作为避免重复打开/关闭和 oplock 等待的设计。
- **推测：** Windows 文件共享是否完全兼容相机软件的具体打开、独占访问、原子替换/重命名、关闭后轮转方式，取决于相机端对同一文件的打开标志与写文件策略。长驻句柄可能在某些相机实现中改变这些操作的时序；也可能完全没有影响。共享标志允许删除本身不能证明相机实际行为不受影响。
- **事实边界：** 在当前代码的正常同路径刷新中，本项目不会每次新开文件；因此“每次刷新重复 CreateFile/oplock”与现有句柄缓存逻辑不一致，不能直接作为已证实根因。新文件切换、句柄失效重开仍可能走打开路径。

### 候选 C：同一 PLC 上的额外读写引入通信/扫描竞争

- **事实：** 本项目可能在分析刷新期间与 PLC 读写；真实调整路径可包含握手读取、调整写入、回读以及完成标志写入。另有可配置的程序号轮询和心跳。
- **推测：** 若相机信号也依赖同一 PLC 的通信通道、CPU 扫描、通信队列或某些共享寄存器/任务，刷新触发的本项目读写可能延迟相机信号处理。用户报告的“PLC 收到相机软件信号变慢”与该路径相容，但代码并未证明两方共用 PLC 资源或协议任务。
- **事实边界：** 若处于模拟 PLC 模式、刷新决策没有触发 PLC 通信，或摄像机信号走独立 PLC 网络/通道，本候选解释力会明显不同。现场模式未知。

### 候选 D：本机 CPU、磁盘、线程池、UI/GPU 等资源短时竞争

- **事实：** 文件读取在线程池执行；决策和图表预计算涉及 CPU；图表更新在 WPF Dispatcher 执行；日志采用同步追加写入。UI 加载遮罩不直接阻塞另一个进程。
- **推测：** 同一电脑上相机采集/图像分析较敏感时，刷新的同步 CPU/磁盘/GPU 负载或后台线程池延迟可能引起画面冻结，表现为与刷新同时发生。默认窗口有限，纯 CSV 尾读负载看起来较小，但配置可以改变窗口大小，且图表计算处理的是返回数据。
- **事实边界：** 目前没有 CPU、磁盘队列、GPU、线程调度或每阶段高分辨率耗时数据，不能据代码推断卡顿确由本机资源饱和。

## 7. 必须保护的逻辑（分析边界，不是改动方案）

- **PLC 安全与握手：** 保持 PLC 寄存器语义、地址映射、调整值单位/字序、状态标志握手、读回校验、重连和操作串行化；不能为了减少刷新耗时而假设可跳过这些流程。
- **数据正确性：** 保持按配置路径及最新日期/文件选取、CSV 尾行/部分行处理、时间戳解析、双压头数据对应、窗口大小、调整/重置后的旧数据过滤与分析顺序。
- **控制状态时序：** 保护 WarmUp/Stable/Drift 等判决、按需下发、成功下发后的压头独立时间戳和仲裁状态更新；这些逻辑直接影响闭环行为。
- **并发与生命周期：** 保持刷新防重入、数据源切换/缓存句柄生命周期、PLC adapter 串行通信、心跳暂停恢复，以及异常情况下 `IsLoading` 的复位。
- **对相机数据的只读边界：** 用户描述为只读取相机导出的 CSV。当前代码对目标 CSV只读打开，但目录扫描和文件元数据访问仍会发生；分析/后续变更均不得默认对相机数据有写入权。

## 8. 影响范围

- **直接代码范围：** `CrimpHeightAnalyzer` 的刷新编排、CSV provider、PLC adapter、刷新/PLC 日志及图表渲染。
- **进程间影响：** 代码没有相机软件 API、进程控制或画面操作调用。可能的影响只可能经由共享文件/存储/系统资源，或双方共同依赖的 PLC/网络/设备等外部资源发生；这是当前代码阅读范围内的判断，不代表已排除驱动或操作系统层行为。
- **控制风险：** 改动 CSV 选择/解析或刷新顺序可能影响数据新鲜度与控制决策；改动 PLC 访问次数/并行度可能影响握手及 PLC 安全时序。
