## 1. 逐项裁决

### R1 实施顺序与测量门冲突 —— **ACCEPT**

- **证据**：PLAN §3 写的是“S4 是阶段 2 的前置条件”，停止条件 3 写的是“没有相关性就停止阶段 1 之后的工作”；但 Handoff 的实施表把 S4 排在 S13 之后。同一个构建里虽然可以靠开关模拟旧行为，但 S5（日志后台化）和 S6（图表计算移到后台）**没有开关**，所以 T1 测到的不是现状行为。
- **对计划的影响**：
  - 拆成两个构建：**构建 A = S0～S3**，行为与现状一致，只多 perf 日志；**构建 B = S5～S11、S13**。
  - perf 日志的后台队列在 S3 建立，只给 perf 日志用；`WriteLogToFile` 到 S5 才接入。因此构建 A 的 PLC 日志写入方式与现状完全一致。
  - **测量门是部署门，不是编码门**：构建 A 交付现场跑 T0/T1/T3 期间，开发可以继续写 S5 之后的代码；但构建 B 必须等用户审阅测量结论后才能部署。
  - 停止条件 3 改为：不部署构建 B，已写的代码保持未合并，回报用户。
  - 用户已确认的阶段 2 行为（Q2/Q4a/Q5）仍然有效；测量门的作用是“先归因，再部署”，不是重新征求同意。

### R2 S9 无法保证 60s —— **ACCEPT**

- **证据**：原规则“旧文件 60s 不增长才重扫”在旧文件持续增长时根本不会触发，最多要等 300s 强制重扫；即使旧文件停止增长，也要再等一个刷新周期（开发机是 20s，合计约 80s）。重扫只在 `DispatcherTimer` Tick 时执行（`_refreshTimer.Tick += async ... RefreshDataAsync()`），而且 `IsLoading` 为真时 Tick 会被直接跳过。
- **对计划的影响**：
  - 作废“空闲 60s”和“强制 300s”两个条件，以及 `RescanWhenIdleSeconds`、`ForceRescanSeconds` 两个开关。
  - 新规则：距上次扫描 ≥ `max(0, NewFileMaxLatencySeconds − RefreshIntervalSeconds)` 时重扫（`NewFileMaxLatencySeconds` 默认 60）。跨天时重扫；文件消失时在同一次刷新内立即重扫，这两条保留。
  - 时限定义：从新 CSV 出现在目录中，到 `LastUsedFilePath` 切换，≤60s。前提是每次刷新都在一个刷新间隔内完成；Tick 被跳过时最坏多一个间隔，需要在 perf 日志中可见。
  - 收益说明：刷新间隔 20s 时扫描次数约减半；间隔 ≥60s 时 S9 没有收益，H1 主要靠 S8。产线刷新间隔**待确认**（不阻塞开工）。
  - 同步修订 AC-B02：旧文件停止增长和仍在增长两种情况都要测，并测量实际耗时。

### R3 PLC 时间戳与延迟指标 —— **PARTIAL**

- **接受的部分**：AC-N03 原文没有定义延迟的起点和终点，也没有说明时钟对齐的要求，确实不可判定。
- **不接受的部分**：说“不可测”过度了。用户的原始描述是“PLC 接受到相机软件的信号时间变长，大约满 200ms”，说明 PLC 侧**已经在用自己的时钟测一个间隔**。最可能是“PLC 发出触发 → 收到相机结果”，起点和终点都在 PLC 时钟上，不需要 PC 时钟参与。
- **对计划的影响**：
  - 定义主指标 **L** = PLC 在自身时钟上测得的“触发 → 收到相机信号”间隔。L 是否就是用户说的“约 200ms”，以及 PLC 能否同时记录这两个时刻：**待确认**，在现场测量开始前确认。
  - 备选指标：如果 PLC 只能记录收到时刻，改用相邻两次收到信号的间隔相对节拍周期的偏差。
  - PLC 与 PC 的时钟偏差只用于把 L 和刷新时刻对齐到 ±1s 窗口内；测量开始和结束时各记录一次，精度 ≤100ms 即可。
  - 同步修订 AC-N03 与 ACCEPTANCE §3。

### R4 AC-D01 / D02 缺少观测通道 —— **PARTIAL**

- **证据**：`CsvDataProvider` 和 `GetLatestDataAsync` 都是 public，可以从外部调用；但现有界面只显示条数、首尾时间戳和统计值。`PrepareChartData`、`ChartData`、`ApplyChartData` 都是 private。另外复核时还发现：`ComputeRobustTrendRange` 同样读取 `Settings.Controller`，S6 的快照必须一并传入，否则会跨线程读取 Settings（复核报告没有指出这一点）。
- **对计划的影响**：
  - **AC-D01 保持逐条严格一致**，验证方式改为**仓库之外**的临时 harness：一个控制台工程（`net8.0-windows` + `UseWPF`），用 ProjectReference 引用应用工程，逐条导出数据。基线版本用 `git worktree add` 在仓库外检出 HEAD。`CsvDataProvider.cs` 不在散点图未提交改动的范围内，所以 HEAD 版本就是基线。worktree 中没有 `bin\...\HslCommunication.dll`，需要先复制过去。harness 和 worktree 都不提交，用完删除。“不新增文件”这一约束针对的是仓库源码，不限制仓库外的临时工具。
  - **AC-D02 收窄**为两项：一是代码差异审查，两个函数除了 `Settings.Controller.X` → 快照字段之外，函数体没有其他改动；二是 UI 可观察量对比。不新增测试工程，也不用反射访问 private 成员。
  - 为了让 harness 和现有调用都能用，S9 需要的新参数通过构造函数的**可选参数**传入；三处 `new CsvDataProvider(...)` 调用（`InitDataProvider`、`PollRecipeAsync`、`SwitchRecipeAsync`）都要传入新参数。

### R5 日志队列结构与关闭语义 —— **ACCEPT**

- **证据**：PLAN 写的是 `Channel<string>`，Handoff 写的是 tuple，两者不一致。`Cleanup` 会被调用两次：`MainWindow.Closing` 一次，`App.OnExit` 一次。在磁盘卡住时，“1s 内退出”和“保证全部落盘”无法同时满足。
- **对计划的影响**：
  - 统一消息类型为 `readonly record struct LogEntry(string FilePath, string Line)`，队列为静态的 `Channel<LogEntry>`（无界、单读者）。
  - 关闭语义：`Cleanup` 必须幂等，第二次调用直接返回；完成写端后最多等待 1s，超时就放弃剩余条目并退出，不阻塞关闭。
  - AC-E04 拆成三种情况：磁盘正常时全部落盘；磁盘卡住时等待 ≤1s 后放弃剩余条目；`Cleanup` 被调用两次时不报错。PLAN 的 E7 和 §5 同步修订。

### R6 AC-R02 表述过强 —— **ACCEPT**

- **证据**：心跳的 Tick 处理是 `async (s, e) => await SendHeartbeatAsync()`；`Stop()` 只阻止新的 Tick，不会取消已经开始的写入。
- **对计划的影响**：AC-R02 改为“刷新期间不启动新的心跳 Tick；已经在执行的写入允许完成（现有行为）”。代码不做改动，心跳和 PLC 时序仍属禁止修改项。

### R7 目录扫描的描述与 AC-D05 —— **PARTIAL**

- **不接受的部分**：复核报告说 PLAN 声称“对每个 JPG 做属性查询”，与 PLAN 原文不符。PLAN 的 R3 写的是“扫描全部目录项”，加上“对每个 **CSV** 调用 `File.GetLastWriteTimeUtc`”。另外，.NET（Core 及以后）的 `FileSystemEnumerator` 在 Windows 上不把通配符交给 `NtQueryDirectoryFile`，而是读出全部目录项后在托管代码中匹配，所以“扫描全部目录项”的说法成立（依据是 .NET 运行时实现，待 ProcMon 证实）；但这一过程不会对 JPG 逐个打开或查询属性。
- **接受的部分**：实际成本和 ProcMon 中呈现的事件形态取决于文件系统和过滤驱动，不能预先写成事实；AC-D05 按字面计数可能无法判定。
- **对计划的影响**：
  - PLAN 的 R3 补充上述限定，标注为“基于运行时实现，待 ProcMon 证实”。
  - AC-D05 改为：先在构建 A 或 `CachedFileLocate=false` 下采集基线，再按实测事件名比较次数和总耗时；如果这些事件在基线中根本不可见，记为“无法判定”。
