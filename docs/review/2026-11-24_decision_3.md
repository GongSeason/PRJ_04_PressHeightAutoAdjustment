## R10 Q2 的“60s”是绝对上限还是相对现状 —— **PARTIAL**

- **接受的部分**：用户的答复是“60s 内识别即可”，原文没有说明这是绝对上限还是相对现状，确实存在歧义。第 2 轮裁决把它解释为“相对现状不新增延迟”，属于推测，应当标注出来并向用户说明。
- **不接受的部分**：不接受把它作为构建 B 部署或 S9 验收的**阻塞项**。证据如下：
  - CSV 只在 `_refreshTimer.Tick` 时定位和读取（`SetupTimer`）。在**现状代码**下，刷新间隔 R >60s 时，新文件最早也要到下一次刷新才被发现，时延上界就是 R。也就是说，“60s 绝对上限”在 R >60s 时**现状本来就做不到**，S9 在这个区间与现状逐行等价（阈值为 0，每次刷新都扫描）。
  - 在 R ≤60s 时，S9 保证 ≤60s，满足任一种解释。
  - 所以 S9 在任何 R 下都不会引入新的退化。按“绝对上限”解释时，不满足的根源是刷新间隔配置，不是 S9；要解决它就得缩短刷新间隔（改变现有配置语义）或增加独立扫描（与本计划目标相反），这两项都超出本计划范围。
  - 开发机的刷新间隔是 20s，落在无歧义的区间内；产线刷新间隔仍**待确认**。
- **对计划的影响**：
  - S9 的规则和代码设计不变。
  - AC-B02 的 90s 用例判定改为“与现状等价”（时延 ≤R，并且每次刷新都重扫），不再表述为“满足 Q2”。
  - 在交付报告中**向用户说明**：如果产线 R >60s，新 CSV 的识别时延 ≤R，这与现状相同，不是 S9 引入的；如果用户需要绝对的 60s，应当另行决定是否把刷新间隔改到 ≤60s（**待确认**，不阻塞构建 A/B）。
  - 补充到 PLAN 的 S9 段、ACCEPTANCE 的 AC-B02，以及 Handoff 的待确认项。

## R11 新增 Performance 数值配置缺少无效值保护 —— **ACCEPT**

- **证据**：
  - `RefreshDataAsync` 第 495 行 `var progressTimer = new DispatcherTimer { Interval = ... }` 位于 `try` 块**之前**。如果间隔改为来自配置，负值会让 `DispatcherTimer.Interval` 抛出 `ArgumentOutOfRangeException`，而且发生在 catch/finally 的保护范围之外：`IsLoading` 已经设为 true 却不会复位（之后所有刷新都会被守卫挡掉），心跳也已经 Stop 而不会恢复。值为 0 时不会抛异常，但定时器会连续触发，造成 UI 繁忙，与本计划目标相反。
  - `SettingsService.Load` 目前只对 `Controller`、`Plc` 做 `??= new()`，不校验数值。
  - `Settings` 只在两处被赋值，都通过 `_settingsService.Load()`（构造函数第 72 行，以及 `ToggleSettings` 取消时的第 411 行）；设置面板也不暴露 `Performance` 字段，所以这些值只能通过手工编辑 JSON 修改。**在 `Load` 中统一归一化可以覆盖所有入口。**
- **裁决（统一策略）**：
  1. 新增 `PerformanceSettings.Normalize()`，在 `SettingsService.Load` 中 `settings.Performance ??= new();` 之后调用。规则如下：
     - `ProgressTextIntervalMs < 250` → **钳制为 250**（与原来的硬编码值一致，即退回现状行为）；
     - `NewFileMaxLatencySeconds ≤ 0` → **回退为 60**（默认值；0 或负数的语义不明确，不把它们解释为“每次扫描”）；
     - 布尔字段不需要处理。
     - 每次归一化都输出 `Debug.WriteLine`，并在 `PerformanceSettings` 中记录被修正的字段名列表（例如 `NormalizedFields`，加 `[JsonIgnore]`），供 perf 日志在启动时记一行。
  2. **纵深防御**：`RefreshDataAsync` 使用间隔时仍写 `Math.Max(250, ...)`；构造 `CsvDataProvider` 时传入的阈值仍按 `max(0, latency − R)` 计算。这样即使有绕过 `Load` 的赋值路径，也不会抛异常或出现负阈值。
  3. 归一化后的值会在用户下次点击“保存设置”时写回 JSON。这是预期行为，与 E9 一致。
  4. JSON 类型错误（例如把数字写成字符串）会导致反序列化失败，`Load` 的现有 catch 会返回 `new AppSettings()`，**整份配置回到默认值**。这是**现有行为**，本计划不做改动，只在风险表中注明。
- **对计划的影响**：更新 PLAN 的 S1 以及风险表（新增 E16）；ACCEPTANCE 新增 **AC-R08**；Handoff 的 S1 行和注意事项同步更新。不阻塞构建 A：S1 属于构建 A，归一化随 S1 一起实现。
