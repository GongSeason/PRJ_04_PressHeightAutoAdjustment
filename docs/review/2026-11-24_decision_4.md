## R12 perf 启动配置记录与“每次刷新一行”的行数冲突 —— **ACCEPT**（采用方案 1）

- **证据**：
  - R11 裁决要求 perf 日志在启动时记一行有效配置；S3 和 AC-N01 只定义了刷新记录，并要求“10 次刷新恰好新增 10 行”；AC-R08 又要求有“启动行”。三者确实互相冲突，而且都没有定义记录类型。
  - `MainViewModel` 构造函数在 `Settings = _settingsService.Load()`（第 72 行）之后，已经在 `SetupRecipePolling` / `SetupHeartbeat` 中通过 `WriteLogToFile` 写启动日志。可见“在构造函数中、Load 之后写一条启动记录”与现有代码模式一致，可以拿到 `NormalizedFields`。
  - `EnablePerfLog=false` 时，如果 AC-R08 依赖 perf 日志，就会依赖一个已经关闭的功能，复核报告的这一点也成立。
- **裁决**：
  1. **同一个 `perf_yyyyMMdd.log`，每行第一个字段是记录类型**：`type=refresh`（每次通过入口守卫的刷新写一行，在 `finally` 中写）或 `type=config`（启动时写一行）。
  2. **`type=config` 的写入时机**：只在 `MainViewModel` 构造函数中 `Settings = _settingsService.Load()` 之后写**一次**。内容包括全部 `Performance` 生效值和 `NormalizedFields`（为空时写 `normalized=none`）。取消设置面板时会重新 `Load`，此时如果有字段被修正，只输出 `Debug.WriteLine`，不再写 config 行（设置面板不暴露这些字段，这种情况只会在运行期间手工改了 JSON 时出现）。
  3. **`EnablePerfLog=false`**：不写 perf 日志。如果 `NormalizedFields` 不为空，通过现有的 `WriteLogToFile` 在 `plc_*.log` 中写一行 `[配置] Performance 字段已修正: <字段列表>`，与构造函数中已有的 `[心跳] 已启动` 这类启动日志做法一致；`NormalizedFields` 为空时不写。
  4. **AC-N01** 只统计 `type=refresh` 行；`type=config` 不计入。**AC-R08** 按 `EnablePerfLog` 分两种判定。
  5. 方案 2（单独的配置日志文件）不采用：会多出一个文件，现场也要多收集一份。方案 3（并入第一条刷新记录）不采用：要等到第一次刷新才能看到，而且用户可能不立即启动自动运行。
- **对计划的影响**：
  - PLAN S3：补充记录类型和 config 行的写入规则。
  - ACCEPTANCE：修订 AC-N01、AC-R08。
  - Handoff：修订 S3 行，补充注意事项。
  - 不影响构建 A / B 的划分、测量门和禁止事项。
